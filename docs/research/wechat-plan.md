# 微信首版方案核查

查证日期：2026-10-02（Asia/Shanghai）。只读取 Server酱官方公开文档、当前官网引用的静态脚本和公开套餐接口；未使用用户账号、未登录、未调用推送或付款接口。用户已确认微信优先、接受第三方注册和少量付费；下述平台与结构仍是工程推荐，不是用户已采纳的决定。

## Server酱 Turbo 的实际阅读体验

推荐候选为 Turbo 的微信服务号通道：用户微信扫码注册、取得 SendKey、保持关注接收服务号，应用以 HTTP POST 发送 Markdown。

**付费也不能据此承诺在服务号会话卡片展开完整日报。** 官方通道对比明确：免费卡片仅标题；订阅会员一般可显示标题和内容，但**微信服务号通道除外**。企业微信应用通道可完整显示，需额外企业微信配置，不属于本首版默认方案。正常阅读路径应设计为“微信通知 → 点击 Server酱详情阅读 → 需要历史时点击公开 GitHub Markdown 日报”。依据：[官方通道对比](https://sct.ftqq.com/docs/getting-started/channels/)、[官网实际加载的首页说明](https://sct.ftqq.com/md/index.md)。

每日 1 份合并简报即可，不逐篇通知。免费 5 条/日足够日常简报及少量告警；会员上限为每日 1000 次 API 请求、每分钟 50 条。因此“愿意少量付费”不等于需要为了本应用的发送条数立即购买。新账号有 7 天全功能试用，可先检验接收和阅读体验。依据：[官方 FAQ](https://sct.ftqq.com/docs/getting-started/faq/)、[获取 SendKey](https://sct.ftqq.com/docs/getting-started/sendkey/)。

## 套餐与保留期

公开订阅页当前加载的 `/sales` 接口返回：1 个月 8 元、12 个月 39 元、60 个月 180 元；接口分别以 31、372、1860 天定义时长，价格字段是分，官网除以 100 显示元。仅做报价核查，不购买。依据：[官网订阅页](https://sct.ftqq.com/subscribe)、[官方公共套餐接口](https://sctapi.ftqq.com/sales)。

近期官方 FAQ 和通道页将免费详情保留期列为 1 天、订阅会员 3 天；官网实际加载的 `md/index.md` 也相同。**不能用 Server酱详情作为永久存档。** 但订阅页加载的另一份未标更新时间的 `md/price.md` 仍列 7 天，并同时保留免费每日 10 条、每分钟 5 条等冲突数字。它与明确标为唯一口径的近期文档不一致，看起来是旧表（推断）；设计按 1/3 天口径，不把 7 天作为承诺。真实到期行为仍需部署时用用户账号验证。依据：[FAQ](https://sct.ftqq.com/docs/getting-started/faq/)、[通道页](https://sct.ftqq.com/docs/getting-started/channels/)、[首页表](https://sct.ftqq.com/md/index.md)、[存在冲突的订阅说明表](https://sct.ftqq.com/md/price.md)。

建议用户先试用；满意后可选择 8 元/月或 39 元/12 个月。付费主要改变额度和服务端短期保留，服务号卡片例外仍存在。最终是否购买、期限与实际支付价格由用户决定。

## 正文长度、格式与状态确认

当前官网引用的主脚本包含 SendKey 页面实际参数说明：`title` 最长 32；`desp` 支持 Markdown，最大 **32 KB**；`short` 最长 64。数值长度以官方页面文字为准，未通过用户凭证做服务端边界实验。实现建议将正文上限作为字节预算，按 UTF-8 计算并留余量，不把 32 KB 误当 32000 个中文字符；超长时缩减标题清单或按论文边界分条，不能截断一篇的实验/结论。正文不支持 HTML。依据：[SendKey 页面](https://sct.ftqq.com/sendkey/)、[官网当前引用的公开主脚本](https://fox.ftqq.com/sct/static/js/main.8e58423a.chunk.js)、[格式 FAQ](https://sct.ftqq.com/docs/getting-started/faq/)。

发送接口返回成功仅表示加入异步推送队列。当前官方页面明确可用返回的 `pushid` 和 `readkey` 查询：

```text
https://sctapi.ftqq.com/push?id={pushid}&readkey={readkey}
```

`wxstatus` 是微信接口返回内容，空值可能表示任务还未执行。应用应保存非敏感推送请求标识，有限次数延迟查询，区分 queued、平台发送结果和未确认；这些是工程状态建议，并非官方已经替本应用提供事务语义。微信接口成功也不是用户已收到、已读或能保证一定弹通知的回执。公开文档没有证明存在可供本应用使用的用户已读回执或服务端幂等键，因此不能许诺恰好一次送达。依据同上 [当前官方脚本](https://fox.ftqq.com/sct/static/js/main.8e58423a.chunk.js) 中的“查询推送状态”说明。

**`readkey` 与 SendKey 都按敏感凭据处理。** 公开仓库、状态分支、日志和日报不能保存其明文，也不能保存带真实 readkey 的查询 URL。首版建议在同一次 run 的内存中完成查询，公共状态仅记录非敏感的 pushid、时间、结果和“未确认”标记；若跨 run 查询确需 readkey，必须另行确认安全加密/Secret 引用方式或采用明确的未知状态恢复策略。此建议不引入额外外部服务、不自动注册账号，具体方案留待状态设计确认。

开发阶段应使用实际 API 返回结构确认 `wxstatus` 的序列化方式及业务错误字段，不沿用只检查 HTTP 200 或顶层 `code=0` 即把日报记为已投递的旧教程。若请求超时但服务端可能已接受，盲目再次发送可能重复，用户需要选择偏少漏还是偏少重复。

## 推荐的日报结构（尚待用户确认）

- 日期、入选/已总结/失败待重试数量。
- 每篇：英文标题、主题标签、arXiv 链接，然后中文背景/贡献/方法/实验/结论五段六句目标，保留实验数字和章节/页码出处。
- 超量清单：标题、链接和简短相关理由；篇数与清单长度依用户之后确认的排序/上限规则。
- 末尾：固定公开 GitHub 仓库内当日日报 Markdown 链接，作为长期存档入口；无须新增 GitHub Pages、网站部署或额外 Web 服务。

正常情况每天合并发送 1 条。先保存完整日报，再发送其 Markdown 内容及存档链接；超长时保证公开存档完整，通知体按已确认的长度策略处理。当天部分成功时发送可用论文并写明待处理数；完全无匹配且采集完整则静默，不能把采集失败伪装成无结果。

GitHub 链接在微信内的打开体验和网络可用性尚未实际验证；Server酱详情内应能直接看到主要总结，避免只发一个可能不便打开的存档入口。用户允许公开的只有 code/config/日报等非秘密内容，不包括 API key、SendKey、readkey 和带凭据的 URL。

## 下一轮必要问题建议

以下是问题草案，供主代理与其他分支合并后发出，尚未正式向用户提出。

❓ **微信平台与阅读方式**：是否接受 Server酱 Turbo 服务号，点击详情直接读完整 Markdown 日报，再以公开 GitHub Markdown 链接查历史？愿意先用 7 天试用，确认体验后自行选 8 元/月或 39 元/12 个月吗？会员也不能保证服务号卡片直接展开完整总结。

➡️ 推荐采用该路径，先试用验证，再按实际需要选择订阅期限；不增加 GitHub Pages。

❓ **不确定投递时的取舍**：发送超时或平台结果迟迟未确认时，希望自动重发以减少漏推（可能重复），还是先等待平台查询结果、次日补发以减少重复（可能延迟）？

➡️ 推荐先查询/重试确认，确认失败才重发；长期无法确认时在下一次运行以补发标记重试，接受偶尔重复。最大重试/确认时长和补采范围可合并入恢复策略问题。

当前尚不需要用户发送密钥；注册、订阅、Secrets 配置及实际到达测试留给开发部署阶段。
